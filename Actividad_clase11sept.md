## Paso 1 - Inconvenientes principales

| # | ¿Cuál es el inconveniente principal? | ¿Qué está cambiando o va a cambiar? | ¿Qué no debería reescribirse cada vez? | ¿Qué se mezcló que no debía? |

| 1 | Varias funciones se repiten en cada página, como revisar la sesión para ver si sigue activa. | La duración de la sesión, la forma de registrar la actividad y el diseño del encabezado. | El funcionamiento de cada trámite, como registrar pedidos, cobrar o consultar un envío. | Las tareas generales de la plataforma se mezclaron con el código de cada trámite. |

## Paso 2 - Inconvenientes principales
| # | Nombre del catálogo, o ninguno | ¿Por qué este? (con algo del relato) | Uno que se parece pero no es (y por qué) |
|---|---|---|---|
| 1 | Ninguno | Tener un panel web y una aplicación móvil al mismo tiempo no es un problema que se resuelva directamente con un patrón GoF. Lo mismo sucede con las fallas del mapa o de la IA, ya que se necesitan otras soluciones para evitar que estos servicios detengan toda la plataforma. | Podría confundirse con Bridge porque existen dos formas de mostrar la información: web y móvil. También podría pensarse en Facade para ocultar los servicios externos. Sin embargo, ninguno de los dos evita por sí solo que el mapa o la IA dejen de funcionar. |
| 2a | Strategy | Cada medio de transporte calcula sus costos de forma diferente. Por ejemplo, una motocicleta no tiene los mismos gastos ni restricciones que una camioneta o un dron. Strategy permite separar esas formas de calcular y elegir la más adecuada para cada pedido. | Template Method también ayuda a organizar distintos procedimientos, pero normalmente parte de una estructura fija. Strategy permite cambiar de forma más sencilla todo el cálculo dependiendo del medio de transporte. |
| 2b | Strategy | El tiempo de entrega puede calcularse de diferentes maneras según el tráfico, el clima, la distancia o el vehículo utilizado. Strategy permite tener varias formas de hacer ese cálculo y elegir la que mejor funcione en cada situación. | State puede parecer adecuado porque también cambia el comportamiento de un objeto. La diferencia es que State depende de una etapa, como "Pendiente" o "En camino", mientras que aquí se quiere cambiar la forma de calcular el tiempo. |
| 3 | Factory Method | La plataforma trabaja con camionetas, motocicletas, bicicletas y drones, y después podrían agregarse más medios. Factory Method ayuda a crear el tipo de transporte necesario sin llenar el sistema de condiciones cada vez que aparezca uno nuevo. | Builder sirve para construir poco a poco un objeto con muchos datos u opciones. En este caso, el problema principal no es cómo construirlo, sino decidir qué tipo de transporte se debe crear. |
| 4 | Observer | Cuando cambia el estado de un pedido, varias personas y partes del sistema necesitan enterarse, como el cliente, el repartidor, el administrador y las estadísticas. Observer permite avisarles a todos sin colocar todos esos avisos dentro del mismo bloque de código. | Mediator también organiza la comunicación entre varias partes, pero se usa cuando distintos elementos necesitan comunicarse entre sí. Aquí solamente se necesita que el pedido informe un cambio a todos los interesados. |
| 5 | Decorator | Un envío puede incluir servicios extra, como seguro, entrega urgente o manejo especial. Decorator permite agregar esos servicios según lo que necesite cada cliente, sin crear una clase diferente para cada combinación posible. | Composite también permite juntar objetos, pero se usa principalmente para formar grupos o estructuras. Decorator se enfoca en agregar características nuevas a un envío que ya existe. |
| 6 | Adapter | Cada proveedor de IA puede responder de una manera diferente. Uno puede enviar JSON, otro XML y otro un objeto propio. Adapter permite traducir todas esas respuestas a un mismo formato que la plataforma pueda entender. | Facade también puede hacer más sencillo el uso de un servicio, pero su objetivo es ocultar la complejidad de varias funciones. Adapter se necesita cuando dos partes manejan formatos diferentes y no pueden comunicarse directamente. |
| 7 | Facade | La plataforma debe utilizar mapas, pagos, notificaciones y otros servicios. Facade puede ofrecer una entrada más sencilla para usarlos, evitando que el panel web y la aplicación móvil tengan que conocer todos los pasos internos de cada servicio. | Adapter puede confundirse con Facade porque ambos ayudan a conectar partes del sistema. La diferencia es que Adapter traduce una interfaz incompatible, mientras que Facade reúne varios servicios detrás de una forma más sencilla de utilizarlos. |

## Paso 3 - Un conflicto y el cliente web + móvil

1.  Qué harían  **mañana**  si no pueden rehacer todo el sistema: el primer corte, no la arquitectura soñada.
> Comenzaríamos por las funciones básicas que se repiten en todas las páginas, principalmente la revisión de la sesión, el manejo de los tokens, la bitácora y el encabezado. Como primer corte, las separaríamos de los archivos de cada trámite para manejarlas desde un solo lugar. Así, si después cambia la duración de la sesión o la forma de validar los tokens, no sería necesario modificar todos los archivos. Consideramos que este paso es el más importante para mantener una sesión estable y nos facilita el funcionamiento del resto de la plataforma.


2.  Qué parte  **no**  tocarían al hacer ese corte.
> No tocaríamos todavía las funciones más específicas, como la generación del PDF, ni intentaríamos cambiar al mismo tiempo los medios de entrega, los proveedores de IA o los servicios externos. Aunque algunas de estas tareas puedan parecer sencillas, primero buscaríamos las funciones que se repiten y afectan a toda la plataforma, con la intención de que el primer cambio sería pequeño y no pondría en riesgo partes que todavía funcionan.

3.  Cómo se nota que hay  **web y móvil**: ¿el mismo trámite se ve distinto en el panel y en el teléfono? ¿Qué tendría que quedar igual en los dos (el pedido, el estado, el medio) y qué sí puede cambiar (HTML con mapa frente a un JSON corto)?
> Se nota que existen una versión web y una móvil porque ambas consultan el mismo pedido, pero necesitan mostrarlo de manera diferente, los datos principales, como el folio, el estado, el medio de entrega y el tiempo estimado, tendrían que permanecer iguales en las dos aplicaciones. 
Lo que puede cambiar es la presentación, el panel web puede mostrar una página HTML con un mapa y más detalles, mientras que el teléfono puede recibir un JSON corto con solamente la información necesaria para que ambas versiones trabajen con el mismo pedido sin depender de una sola forma de mostrarlo o se mande mucha información que no será necesario a la plataforma opuesta.
